# Design Decisions — Gold Layer

This document explains the *why* behind every table, view, and modeling decision in the Gold layer — not just what exists, but what alternatives were discarded and why. The code already has extensive inline comments (`dwh_architecture/03_gold/*.sql`); this document organizes them into a coherent narrative for someone who didn't live through the design process.

## General principle: when a table, when a view?

Four questions, in order, decide whether a Gold-layer object should be a physical table or a view:

1. **Will something else store a permanent key pointing to this?** If a fact needs a stable FK that survives even if the source data changes tomorrow (an SCD2 surrogate key), it has to be a table — a view has no memory of its own, it can't preserve "this was March's version" once the source data has changed.
2. **Does the source already retain the history I need, or does it get overwritten and I have to accumulate it myself?** If the source is a complete daily mirror with no history (like `silver.sap_bsid`), and you need a trend over time, it has to be a table — the table is what accumulates what the source doesn't retain.
3. **Is filtering/joining the source expensive on every query, and will something query it often?** Even if the source already has history (like `silver.sap_bsad`, which does retain everything), if the filter/join is expensive and a dashboard is going to hit it repeatedly, materializing it into a table with its own index is a valid performance decision — not architecturally mandatory, but practical.
4. **If none of the three apply** — it's just re-arranging/filtering/joining data that's already materialized somewhere else, with no new identity and no need to accumulate — **it's a view**. Recomputing it on every query is cheap and keeps the business logic (which tends to keep evolving) separate from the heavy physical tables.

A fifth question, mostly for ratios/percentages: **will this only ever be consumed from Power BI?** If so, it shouldn't even be a SQL object — it should be a DAX measure. Averaging a ratio that's already computed per row (instead of summing numerator and denominator separately and dividing at the end) gives a mathematically incorrect result at any grain other than the row's exact grain — DAX solves this natively by respecting the filter context.

## Dimensions

### `gold.dim_fecha` — no SCD, growing range
Self-extending calendar: fixed floor at `2022-01-01` (`bronze.sap_bsad`'s real start date), ceiling at `today + 1 year` (a cushion for future due dates, e.g. NET-90 terms), automatically extended on every `gold.load_gold` run. **It used to be static** (2020-01-01 to 2035-12-31, populated once) — redesigned because the Year filter in Power BI offered a full 15 years even though the real data only started in 2022, poor UX. It doesn't need SCD because a date, by definition, never changes its derived attributes (day of week, quarter, etc.).

### `gold.dim_cliente` — SCD Type 1
Customer identity (RFC, name, address). Fully overwritten on every load, **with no version history**, because these attributes almost never change — there's no value in paying the cost of SCD2 (more rows, more temporal-join complexity) for data that is, in practice, static.

**`tipo_cliente` gained a 5th value, `MARKETPLACE` (2026-08-27)**, and `DIRECCION_ALTERNA` was renamed to `SIN_RFC` (same condition, `RFC IS NULL` — just a naming preference, no logic change). `MARKETPLACE` is checked **before every other branch** in the `CASE` — it has to win against `FILIAL`/`SIN_RFC`/`GENERICO`/`PADRE` all at once, because the named accounts it covers span every one of those buckets in real data: Amazon has a real RFC (would otherwise be `PADRE`), most Mercado Libre/Claro Shop variants have `RFC='XAXX010101000'` (would otherwise be `GENERICO`), and the payment-gateway clearing accounts (Mercado Libre/Mercado Pago/Kushky/Conekta "INGRESOS TRANSITORIA", Openpay's clearing account specifically) have `RFC IS NULL` (would otherwise be `SIN_RFC`). Identified by `nombre LIKE`/exact match, not RFC — confirmed against the real 30-account candidate list before writing the pattern (see `dwh-ciosa-project-status.md` in memory). `'OPENPAY INGRESOS TRANSITORIA'` uses an **exact match**, not `LIKE 'OPENPAY%'` — a real, unrelated customer (`'OPENPAY SAPI DE CV'`, RFC `OPE130906HN4`) would have been swept in by a broader pattern; confirmed with the user this must stay out.

### `gold.dim_cliente_comercial` / `gold.dim_cliente_credito` — SCD Type 2, two separate tables (mini-dimensions)

**Why not a single `dim_cliente` with SCD2 for everything**: this is Kimball's **mini-dimension** pattern, applied deliberately. If channel/region/route and credit limit/block lived in the same SCD2 table as customer identity, every time the most volatile attribute changes (`bloqueo_credito`, which changes weekly according to this project's real data) a new row would be generated that also versions the name, RFC, and address — which didn't change. With thousands of customers and weekly changes, the table explodes with near-duplicate rows, and on top of that you can no longer cleanly ask "how did this customer's region change?" without the answer being contaminated by versions that only exist because credit changed.

The rule applied: **group attributes by how often they change together, not by which business entity they conceptually "belong" to**. `dim_cliente_comercial` (channel, region, route, salesperson) changes occasionally; `dim_cliente_credito` (limit, block, risk classification) changes often — each versions at its own pace. The real cost: an analyst needs more joins to put together a complete report — a conscious trade-off, not a free one.

**SCD2 mechanics** (the same in both tables): `id_surrogate` (IDENTITY, the technical key the facts use), business key (`cliente_id`), `hash_atributos` (`HASHBYTES('SHA2_256', ...)` over the tracked columns — supported on SQL Server 2012 SP1, confirmed), `fecha_inicio_vigencia`/`fecha_fin_vigencia`/`es_vigente`, plus a unique filtered index `WHERE es_vigente=1` that guarantees a single active version per customer. Implemented as explicit sequential steps in a temp table (stage → close changed version → insert new version), not a single `MERGE` — easier to debug on this server than compacting everything into one statement.

**`dim_cliente_comercial` keeps `organizacion_ventas`/`canal_distribucion`/`sector`** even though the primary key is just `cliente_id`, so `dim_cliente_credito` can reuse "which channel was already chosen as the customer's representative" when looking up the credit analyst/collector — a single source of truth for that decision, not re-resolved in the second table.

**Facts relate to these two by surrogate key (`Cliente Comercial Sk`/`Cliente Credito Sk`), never directly by `cliente_id`** — the surrogate key is already resolved by date in the ETL to the correct version. A direct relationship by `cliente_id` would apply the customer's *current* attribute to their entire transaction history — the same mistake that led to retiring the `CLIENTE_LEGAL` classification (see below).

### `gold.dim_empleado` — SCD Type 1, conformed / role-playing dimension
Built 2026-08-27. **Why it exists**: `vendedor`/`gerente` (on `dim_cliente_comercial`) and `analista_credito`/`cobrador` (on `dim_cliente_credito`) each carry their own `*_id`/`*_nombre` column pair — the same employee's name can be duplicated as plain text in up to 4 places. `dim_empleado` is Kimball's **role-playing dimension** pattern: one physical table, joined multiple times (once per role) instead of the name being repeated. It's additive, not a replacement — the existing `*_id`/`*_nombre` columns on `dim_cliente_comercial`/`dim_cliente_credito` are untouched; `dim_empleado` just gives "by person" reporting a place to join to.

**SCD1, no surrogate key** (same style as `dim_cliente`): key is `id_empleado` directly (raw `PERNR`, not zero-stripped, so it matches `vendedor_id`/`gerente_id`/`analista_credito_id`/`cobrador_id` with no transformation). Source: new `silver.sap_pa0001`, curated to the 5 `bronze.sap_pa0001` columns any consumer in this project has ever actually used (`MANDT`/`PERNR`/`ENAME`/`BEGDA`/`ENDDA`), filtered to the current record only (`ENDDA='99991231'`) — collapsing SAP's own infotype history to 1 row per employee, since no consumer here has ever needed a past assignment, only "who is this person right now" (passes the silver layer's own filter-vs-flag test).

**No FK constraints added** from `dim_cliente_comercial`/`dim_cliente_credito` to this table, deliberately: SAP end-dates an infotype 0001 row when someone leaves, so a `*_id` captured historically on an SCD2 row can point to a `PERNR` with no current row in `silver.sap_pa0001` — enforcing an FK could break an existing load over an ex-employee with no warning. Joined by `id_empleado` at query time (Power BI relationship or view) instead, same as any other unenforced role-playing dimension.

## Facts

### `gold.fact_saldo_cartera` — periodic snapshot, customer + date
**Why it's a table and not a view**: its source, `silver.sap_bsid`, is a **complete** daily mirror with no history retained (fully reloaded on every run). A view over `bsid` would only ever show "today" — never a trend. The table exists specifically to accumulate a new snapshot every day that the source doesn't retain on its own. **Real consequence of this**: it can't be backfilled historically — it only starts accumulating from the first day its load ran.

**Customer+date grain** (not invoice line): with ~91,593 line items / ~4,568 customers with a balance, line grain would have grown ~33M rows/year on a server with an already-known 2GB log ceiling; customer grain grows ~1.67M rows/year, manageable.

**Scope deliberately left broad (2026-08-27)**: when `gold.vw_cartera_abierta` and `gold.vw_pago_factura_simple` got real-customer scope filters the same day (`canal_distribucion IN (10,20,40,60)`, `tipo_cliente <> DIRECCION_ALTERNA`, `estatus_comercial <> FUERA_DE_ALCANCE`), this fact deliberately did NOT get the same filters. Two reasons: (1) it's the only object in the DWH that answers "how much does the WHOLE company owe, any channel/type" — narrowing it in place deletes that number from the model entirely; (2) it's a periodic snapshot that **cannot be backfilled** — narrowing it in place would create a permanent discontinuity between already-accumulated broad-scope history and future narrow-scope snapshots. `vw_cartera_abierta` carries the scoped version instead, as a view (zero risk to accumulated history).

**DPP / % on-time-late removed (2026-08-27)** - NOT rebuilt as a SQL object at all. It had been living here since the 2026-08-19 migration off the deleted `fact_aplicacion_pagos`, but its source (`vw_pago_factura_simple`, itself built on `fact_pagos_compensados`/`fact_facturas_compensadas`) already retains full history since 2022. A `gold.vw_comportamiento_pago_cliente` view was drafted first, then retired same-day: a live view only ever shows "DPP as computed right now," it can't show a real trend ("what did DPP look like 3 months ago") without re-running against historical data. The user chose to compute the DPP trend as a **Power BI DAX time-intelligence measure** directly over `gold.vw_pago_factura_simple`'s `fecha_pago`/`dias_pago` columns instead - same pattern already used for credit utilization (DAX, not SQL, per this document's 5th table-vs-view question). If DAX time intelligence ever proves too slow over the real data volume, the fallback is a genuine periodic-snapshot fact (monthly grain, `cliente_id` + `mes_corte`) - not a view, for the same reason `fact_saldo_cartera` itself is a table.

### `gold.fact_pagos_compensados` / `gold.fact_facturas_compensadas` — filtered mirror of `bsad`
**Names**: renamed from `fact_pagos`/`fact_facturas` (2026-08-21) — the original names over-promised scope. They only contain documents that are already **compensated** (settled), not every payment/invoice that exists — the name now says so explicitly.

**Why they're a table and not a view, applying criterion 3 (not 1 or 2)**: unlike `fact_saldo_cartera`, here no other table stores a surrogate key pointing to them (criterion 1 doesn't apply), and their source (`silver.sap_bsad`) **does** retain complete history since 2022 — it's never overwritten (criterion 2 doesn't apply either). The real reason for materializing them is **performance**: full `bsad` has ~11.9M rows across every document type; filtering live (`clase_documento='DZ' AND (sgtxt='Asignación Aut. Deposito' OR sgtxt LIKE 'BB%') AND debe_haber<>'S' AND monto>0` for payments, `clase_documento IN (F1-F6)` for invoices) on every dashboard query would be much slower than querying 611K/4.6M already-filtered rows with their own index (`IX_..._grupo` over `documento_compensacion`+`ejercicio_compensacion`, added after confirming that `vw_pago_factura_simple`'s join without it scanned the full table every time). It's a conscious performance decision, not a hard architectural requirement.

**Raw-payment filters, iterated with real evidence**: `debe_haber<>'S'` was added after finding that 4 of 5 sample "ambiguous" groups were actually a single real payment duplicated by its own mirror/offsetting line (same document, same amount, same text) — applying the filter reduced July's ambiguous residual from $1.52M to $249K. `monto_moneda_local>0` was added afterward after finding that 6 of the remaining 14 groups were the child's own "H" line with a $0.00 amount (a technical residual) inflating the candidate count.

**Text filter, 3 iterations in one day (2026-08-29)**: `sgtxt = 'Asignación Aut. Deposito'` → `sgtxt IS NOT NULL` → `sgtxt = 'Asignación Aut. Deposito' OR sgtxt LIKE 'BB%'`. The original exact-text match was too strict, discovered while reconciling July against a real SAP export (`PAGOS DZ (2).xlsx`) that showed a $13M gap. Real data check: 99.3% of that month's DZ rows in SAP carry *some* line-item text, not always that literal phrase — a large multi-invoice payment (one customer, one deposit, reallocated across 9 invoices by SAP) had each reallocation line lose the exact phrase, so the whole $1.28M silently disappeared from the fact table. An earlier fix attempt tried to specifically detect and re-admit these reallocation lines with self-reference/near-duplicate-amount heuristics — discarded after realizing it would have **double-counted** that payment (SAP's own report only ever lists the original deposit once; the 9 reallocation lines are internal bookkeeping, not separate cash). `sgtxt IS NOT NULL` fixed that exclusion, but proved too *loose* in the other direction: it let through `CHEQUE DEVUELTO` (a **bounced** check — not real collected cash) and a long tail of unreviewed reference texts (SPEI, DEPOSITO DE TERCERO, PAGO FACTURAS, etc.) whose legitimacy as real cobranza was never confirmed with someone who owns these business rules. **Final, deliberately conservative**: only `'Asignación Aut. Deposito'` and `'BB%'` (bank reference codes) — covers 98.6% of July's non-null-sgtxt population ($166.5M of $168.85M) while excluding `CHEQUE DEVUELTO` and every other unreviewed pattern. Known to under-count vs. `IS NOT NULL` on purpose — don't widen it again without that business-rule confirmation. See `dwh-ciosa-project-status.md` in memory for the full investigation and the catalog of patterns still pending review.

**Investigated but deliberately NOT implemented (2026-08-29): a same-group "sibling" text signal exists for part of the blank-`sgtxt` population.** Some deposits with a blank `sgtxt` on their own `'H'` line have a self-referencing sibling `'S'` line in the *same* compensation group, same amount, that carries the valid `'Asignación Aut. Deposito'` text instead — SAP attached the descriptive text to the technical mirror side rather than the cash side. Checked against real July data: 23 of the ~89 "blank comment" documents from a manual reconciliation follow this exact pattern ($257,488.46), leaving 66 with no text on either side of their group (genuinely unexplained, pending business confirmation, not a code question). A real risk surfaced during validation before anything was written: in multi-hop payment chains (deposit → hijo → nieto, the same chain pattern documented for `fact_aplicacion_pagos` below), an intermediate document can qualify twice under a naive version of this rule — once as the validating sibling for its parent, once as its own candidate toward the next hop — which would double-count the same cash (confirmed 2 such cases in July, 4 across full history). **Deliberately left unimplemented** at the user's request until the chain case has a real resolution, not because it's unsafe in principle — it just isn't finished. See `dwh-ciosa-project-status.md` in memory for the exact validation queries, document lists, and the chain-handling question still open.

**Reconciliation methodology note, not a code change**: while chasing the residual gap against the SAP export, several "missing" payments turned out to have `fecha_documento` (the payment document's own date) in a *different* month than the SAP report's own period bucketing. Two wrong guesses were tested and ruled out with real data before finding the right field: `fecha_documento` alone under-counted (a payment dated June 5th that SAP's export still placed in July), and `fecha_compensacion` (clearing date) over-corrected in the other direction (several real July payments clear in August, so filtering by clearing date pushed them out of July entirely, and SAP's export still had them in July). The field that matches SAP's own report exactly is **`fecha_contabilizacion`** (posting/GL date, confirmed by matching it 1:1 against the export's own "Fecha" column for both a case where it differs from `fecha_documento` and a case where it differs from `fecha_compensacion`). Any future reconciliation against a SAP-side "pagos del mes" export should filter `fact_pagos_compensados`/`silver.sap_bsad` by `fecha_contabilizacion` — `fecha_documento` and `fecha_compensacion` both look like plausible period fields and both produce a residual that reads exactly like a missing-data bug, but neither matches how SAP itself defines the month. `fecha_contabilizacion` is now a real column on `gold.fact_pagos_compensados`, populated by `gold.load_fact_pagos_compensados` — no need to look it up via `silver.sap_bsad` anymore.

**Self-canceling internal pair excluded (2026-08-29)**: a document can carry two of its own lines inside a *self-referencing* compensation group (`documento_compensacion = documento_id`) — one `'S'` line (already excluded by the `debe_haber<>'S'` filter above) and one `'H'` line with the exact same amount, netting to zero. That `'H'` line is an internal reclassification receiving its own reversal, not a second real deposit — but before this fix it counted as a second "candidate" alongside the real payment (a genuinely different document) sharing the same compensation group, making `vw_pago_factura_simple`'s "only relate groups with exactly 1 candidate" rule wrongly treat the whole group as ambiguous and exclude it. Found from a real SAP screenshot of one such group; validated against all of July's ambiguous groups before implementing: resolves 102 of 129 previously-ambiguous groups (+$192,320.13 recovered), while the other 27 groups (genuinely 2+ different real deposits, different amounts) correctly remain excluded as ambiguous ($286,932.22). Fix is a `NOT EXISTS` added to the same filter, checking for a same-document/same-amount/opposite-side `'H'` row before admitting it.

**Backfill kept separate from the incremental load**: `backfill_fact_pagos_facturas_compensados.sql` (complete history since 2022, run once) vs. `gold.load_fact_pagos_compensados`/`load_fact_facturas_compensadas` (incremental, current + previous month) — the same pattern `silver.load_silver` uses for `bsad`, so as not to reprocess 11.9M rows on every daily refresh.

## Views

### `gold.vw_cliente_canal_estatus`
Classifies each customer+channel row from `silver.sap_knvv` as ACTIVO/LEGAL/INACTIVO/REVISAR/FUERA_DE_ALCANCE, ported from a Python script already in use (`ciosa.py`) and validated against real data. **A view, not a table**, because it's pure filter/CASE logic over a table that already exists — nothing is going to reference it by key, it doesn't accumulate anything the source doesn't have. `gold.dim_cliente_comercial` loads *on top of* this view, reducing it to 1 row per customer with the priority criterion ACTIVO > LEGAL > REVISAR > INACTIVO > FUERA_DE_ALCANCE.

**`FUERA_DE_ALCANCE` prefix list extended to include `9` (2026-08-27)**, confirmed by the business while validating `gold.vw_cartera_abierta` — `cliente_id` starting with `9` are not real customers either, same tier as the already-existing `5`/`6`/`7`. Applied at this canonical level (not as a one-off filter in a single report), deliberately, to avoid repeating the 2026-08-17 mistake of conflating "not a real customer" with "real customer out of scope for one report" (see the channel 10/20/40/60 note in the code). Propagating this change through `gold.load_dim_cliente_comercial` only versioned 2 customers — most `9`-prefix accounts were already excluded via channel, not newly caught by this specific condition.

### `gold.vw_pago_factura_simple` — the reporting view
Relates payment↔invoice only when the compensation group has **exactly 1 candidate payment** — if 2+ payments share the same group, there's no way to know for certain which one covered which invoice, so it's left out rather than forcing an arbitrary match (the same "don't guess" principle applied throughout the project).

**Single-RFC-per-group safeguard**: only includes payments whose entire compensation group (all lines, not just payment+invoice) belongs to a single real identity — this allows legitimate `cliente_id` crossovers within the same RFC (the same person/company with several accounts), but excludes batches where genuinely different identities get mixed together (marketplace technical accounts, etc.). Measured: only 0.12% of GENERICO customers' amount falls into groups with 2+ distinct RFCs — the filter excludes exactly that, lets the remaining 99.88% through.

**`COUNT(DISTINCT k.rfc)` → `COUNT(DISTINCT ISNULL(k.rfc, 'SIN_RFC_'+k.cliente_id))` (2026-08-29)**: `COUNT(DISTINCT)` ignores `NULL`s, so a compensation group made up entirely of a single MARKETPLACE customer (RFC `NULL` by design — Kushky, etc.) evaluated to 0 distinct identities, not 1, and failed the `=1` safeguard even though there was no real ambiguity at all — a marketplace account settling a payment by itself, with nothing else in the group. Confirmed against real July data before changing anything: $1.33M recovered (9 payments), $0 lost from what was already correct. The `cliente_id` fallback keeps the original safeguard's purpose intact — a group mixing 2+ genuinely different identities (with or without RFC) still fails the check; only "one customer with no RFC, alone in its group" stopped being miscounted as zero.

**`CLIENTE_LEGAL` was retired (2026-08-20)** from the classification for a historical-reliability reason, not a matter of preference: `dim_cliente_comercial` is SCD2, but each customer's initial version was artificially backdated to `2020-01-01` (just to allow the temporal join with historical facts) — it doesn't represent an actually observed real transition. A customer who became LEGAL a few months ago, with no other captured transition, would show up as LEGAL since 2020 in the temporal join — labeling 2022-2025 payments as `CLIENTE_LEGAL` when that customer was actually paying normally back then. **Lesson that applies to any future SCD2 attribute**: a classification that depends on projecting a *current* attribute backward in time is only as reliable as how far back real transitions have actually been observed.

**GENERICO is included** (reverting a one-day exclusion): the business process owner was shown the full list of generic customers (Mercado Libre, storefront, employees, tests) and confirmed they should be considered — "they're part of the flow."

**`clasificacion_cobranza`'s month-cohort granularity was validated, not just assumed (2026-08-26)**: the CASE compares `fecha_vencimiento`'s calendar month against `fecha_pago`'s calendar month, not the exact day gap between them — so, for example, an invoice due August 1st paid July 31st lands in `PAGO_ANTICIPADO` even though it's one day early. This is intentional for the field's real purpose (a month-cohort attribution feeding the still-unbuilt monthly budget-compliance report — was August's expected cartera collected before August started), but it's a different question than "did this customer pay early/late," which is what the current dashboard actually presents it as. Two possible distortions were quantified against real 2026 data and both came back small: `PAGO_ANTICIPADO` inflated by boundary-crossing payments 1-3 days early is 3.25% of that bucket's amount; `CARTERA_DEL_MES` hiding invoices paid 17+ days late within the same month (using the same grace-period threshold `fact_saldo_cartera` already applies) is 1.9% of that bucket's amount. Both effects are real but too small to justify splitting the classification into a separate day-precise field — `dias_pago` is already exposed on the view for anyone who needs exact-day precision instead of the month-cohort label.

**`monto_pago_asignado` added (2026-08-26) to fix a real fan-out bug, not a minor one**: the view's grain is 1 row per (pago, factura) pair, so when a compensation group settles 2+ invoices at once — measured at 51.6% of all payment groups in 2026 data, the norm rather than an edge case — `monto_pago_virgen` (the raw deposit amount) repeats in full on every one of those rows. Summing it directly inflates the real cash figure by however many invoices share the group: measured at $853.9M real vs. $97,645.0M if summed naively, a ~95x inflation, the same class of over-attribution bug that got the original `fact_aplicacion_pagos` deleted (see "Retired objects" below) — it resurfaced here because this view's join to `fact_facturas_compensadas` was never grain-restricted the way the join to `fact_pagos_compensados` is (`num_pagos_candidatos = 1`). The Power BI model's own `Monto Total Recibido` measure already worked around this via `SUMX(DISTINCT Cobranza[Documento Pago], MIN(...))`, but that protection only covered that one measure — any direct SQL query, or any other DAX measure written without the same pattern, was exposed. Fixed by adding `monto_pago_asignado`: the payment amount split proportionally across the invoices it settled, weighted by each invoice's own amount within the group (`p.monto_moneda_local * f.monto_moneda_local / SUM(f.monto_moneda_local) OVER the group`) — `SUM(monto_pago_asignado)` is now correct with no `DISTINCT` trick required. `monto_pago_virgen` is kept unchanged for anyone who needs the original per-payment-document value on a row, with a comment warning against summing it directly.

**`cliente_comercial_sk` added (2026-08-26) — the star-schema wiring gap is now closed on the real dashboard, not just the portfolio prototype.** A star-schema design with `Cliente`/`Cliente Comercial`/`Cliente Credito` as proper dimensions related by surrogate key (instead of embedding `nombre`/`canal_distribucion`/`estatus_comercial` as plain text on the fact) had already been built and validated with synthetic data in the public `payment-behavior-dashboard` portfolio repo — but the real working dashboard (`powerbi/Comportamiento de Cobranza.pbip`, not tracked in this repo, see the README's Power BI note) kept the denormalized shape. The only piece missing to make it real was exposing `dim_cliente_comercial.id_surrogate` (already resolved via this view's existing temporal join) as a column here. With it added, the real dashboard's `Cobranza` table was rebuilt as `fact_cobranza`/`dim_cliente`/`dim_cliente_comercial` (Kimball-conformed-dimension pattern, `dim_cliente_comercial` also filtered to channels 10/40/60 to match this view's own scope). `dim_cliente_credito` was wired the same way to a new `fact_cartera` (from `gold.fact_saldo_cartera`) for a credit-utilization measure — a separate fact, not related to `Cobranza`, since nothing there needs credit-limit context today.

**`canal_distribucion` scope tried and reverted, same day (2026-08-27)**: channel `20` (retail) was added to the list, then removed again a few hours later once the user reconsidered — this DWH is explicitly scoped to **mayoreo**, so `canal_distribucion IN ('10','40','60')` is unchanged from before. Channel 20 customers ARE real customers (their `estatus_comercial` in `gold.vw_cliente_canal_estatus` was deliberately left untouched) — they're just outside this DWH's mission, a report-scope decision, not a "is this a real customer" one (this project already learned that distinction the hard way once, 2026-08-17, for the same channel list). Reverting also sidestepped a real finding surfaced while validating the channel-20 addition: channel 20 pays almost exclusively via `clase_documento='CP'` (Cobranza POS), which `gold.fact_pagos_compensados` never covers (only `'DZ'`) - see `dwh-ciosa-project-status.md` in memory for the full investigation. Don't re-add channel 20 here without deciding `CP` support first.

**`clasificacion_cobranza` gained `MARKETPLACE`/`Contado`, checked before the date-based branches (2026-08-27)**: real business requirement, brought back by the user after talking to the report's actual stakeholder. Marketplace/payment-gateway accounts (`tipo_cliente='MARKETPLACE'`, see `dim_cliente`'s own section above) and generic/cash-type accounts (`tipo_cliente='GENERICO'`) don't have a real "due date" payment pattern — they're pulled out before the `VENCIDA`/`DEL_MES`/`ANTICIPADO` `CASE` runs at all, rather than forced into one of those 3 buckets. Checked against `k.tipo_cliente` (the **payer**, not `kf`) — same "group by who paid" convention already established 2026-08-26 for `cliente_id` itself. `SIN_RFC` (renamed from `DIRECCION_ALTERNA` same day, same condition) is still excluded entirely from the view — `MARKETPLACE` is a separate `tipo_cliente` value carved out specifically so these accounts stop being caught by that exclusion.

**`tipo_cliente <> 'DIRECCION_ALTERNA'` (2026-08-27)**: already excluded since 2026-08-19, originally inferred from a 10-account sample where 9 were confirmed technical/reconciliation accounts — now a **confirmed** business rule, not an inference. A business-process owner confirmed customers with no RFC are never real customers for cartera purposes.

**`INNER JOIN` → `LEFT JOIN` on `gold.fact_facturas_compensadas` (2026-08-29)**: found during the same July reconciliation investigation as the `sgtxt` fix above. A real, fully valid payment with no invoice in its own compensation group ("pago a cuenta" — measured: 1,411 of 1,426 such July cases have no invoice or any other document at all sharing the group) used to disappear from this view entirely, since the `INNER JOIN` required a match. Now it stays: `clasificacion_cobranza` resolves to `MARKETPLACE` if the payer's `tipo_cliente` is `MARKETPLACE` (unaffected by invoice presence — Kushky-style accounts routinely clear DZ-against-DZ with no invoice at all), or `SIN_FACTURA_IDENTIFICADA` otherwise — documented instead of silently dropped. `monto_pago_asignado` falls back to the full payment amount when there's no invoice to prorate against.

**Ambiguity gate redefined (2026-08-29, later the same day)**: the "don't guess" rule originally excluded any group with `num_pagos_candidatos > 1`, treating 2+ payment documents sharing a group as automatically ambiguous. Found from a real SAP example (2 payment documents — a $10,403.21 deposit and a $0.10 leftover — settling exactly 1 invoice of $10,403.31): with only 1 invoice in the group there's nothing to mis-attribute, since every payment necessarily applies to that same invoice regardless of count. The gate now only excludes a group when **both** sides have 2+ candidates (`num_pagos_candidatos > 1 AND num_facturas_candidatas > 1`) — a genuine many-to-many case where correspondence really is unknowable. `monto_pago_asignado`'s existing proration formula needed no change: with exactly 1 invoice, `suma_facturas_grupo` equals that invoice's own amount, so the formula simplifies to the full payment amount, counted once per payment row. Validated against the 27 July groups the previous fix still excluded: 23 have exactly 1 invoice ($120,710.99, now resolved) and only 4 have many invoices (5/7/10/13 - genuinely ambiguous, $166,221.23) — see the next note for how those 4 are handled.

**`LOTE_CONCILIACION` added (2026-08-29, same session)**: the 4 remaining many-to-many groups from the note above are structurally different from every other case this project has resolved — each carries a `clase_documento='AB'` line (SAP's manual adjustment/reclassification type) as its own self-referencing document. Checked whether any deposit amount subset-sums to a specific invoice or invoice subset in any of the 4 groups — no clean match, so per-invoice attribution here would repeat the exact over-attribution risk that got the original `fact_aplicacion_pagos` deleted. Validated the AB signal against all of July's data: 100% correlation — the 23 groups resolved by the single-invoice rule have zero AB documents; these 4 have exactly one each. Rather than leave real cash excluded from every report, these groups are now included with one row per payment (the invoice join is deliberately suppressed for them, so there's no per-invoice fan-out), tagged `LOTE_CONCILIACION` in `clasificacion_cobranza` with no invoice columns populated — same treatment as `SIN_FACTURA_IDENTIFICADA`, since there genuinely isn't one specific invoice to report per payment. The cash now counts in any measure that sums `monto_pago_asignado` without pretending to know which invoice(s) it covered.

**`clasificacion_cobranza` redesigned again (2026-08-30) — MARKETPLACE/CONTADO/SIN_FACTURA_IDENTIFICADA/LOTE_CONCILIACION removed from it entirely, `estatus_identificacion`/`motivo_no_identificado`/`cliente_credito_sk` added.** Triggered by a Power BI report redesign request — see `powerbi/_brief/pagos-cobranza-rediseno-analisis.md` for the full architecture discussion, evaluated and rejected alternative (a separate `fact_pagos` table), and the real July numbers behind the decision. Three changes:
1. **The 3 real date-based values renamed** (pure rename, same month-cohort logic, unchanged since 2026-08-26): `CARTERA_VENCIDA`→`PAGO_A_VENCIMIENTO`, `CARTERA_DEL_MES`→`PAGO_A_MES`, `PAGO_ANTICIPADO` unchanged.
2. **`MARKETPLACE`/`CONTADO` removed as `clasificacion_cobranza` values** — that was conflating a customer-type attribute with a payment-behavior classification in the same column. `tipo_cliente` (Marketplace/Contado/Mayoreo, mapped from `gold.dim_cliente.tipo_cliente`) now lives only on `dim_cliente`. A Marketplace/Contado payment that has an identified invoice now gets a real date-based value like any other payment; `clasificacion_cobranza` is `NULL` only when no invoice was identified.
3. **`estatus_identificacion` (`FACTURA_IDENTIFICADA`/`FACTURA_NO_IDENTIFICADA`) and `motivo_no_identificado` (`NULL`/`SIN_FACTURA_IDENTIFICADA`/`LOTE_CONCILIACION`) added**, replacing what `SIN_FACTURA_IDENTIFICADA`/`LOTE_CONCILIACION` used to do as `clasificacion_cobranza` values. Named "identificación", deliberately not "conciliación": every payment in this view already comes from `silver.sap_bsad` (already compensated/cleared in SAP), never `bsid` (open/not-yet-applied) — "no conciliado" reads as "still pending," which is never true here. "No identificada" means only that this project couldn't attribute the payment to one specific invoice with certainty.
4. **`cliente_credito_sk` added** (`LEFT JOIN` to `gold.dim_cliente_credito`, same temporal-SCD2-resolved pattern as `cliente_comercial_sk`) — this relationship never existed before (`dim_cliente_credito` was only wired to `fact_saldo_cartera`), needed for Ejecutivo de Crédito/Cobrador analysis. `LEFT JOIN` because not every `cliente_id` has a `silver.sap_knkk` record (same documented gap as `gold.fact_movimientos_compensados`'s own history) — validated 2026-08-30: 99.96% populated (51,932 of 51,954 July rows), the rest legitimately `NULL`.

A 2-physical-table design (`fact_pagos` for every payment vs. `fact_conciliacion` for only identified ones) was seriously evaluated first and explicitly rejected after validating with real July numbers (82.0% identificada/$137.4M, 10.4% no identificada/$17.5M, 7.6% correctly out of scope/$12.75M): `monto_pago_asignado` already makes the mixed grain numerically safe, so splitting into 2 tables would only add 2 SQL objects to keep in sync forever for no additional correctness benefit. Validated after implementing: July total unchanged exactly ($153,502,983.94, same 51,954 rows, same 12,196 distinct payments) — this was a rename/reclassification, not a filter change.

**Known issue found during this validation, NOT fixed (separate from the above)**: `fecha_pago` in this view is `p.fecha_documento`, not `p.fecha_contabilizacion` — the field this project's own July reconciliation investigation (see the `gold.fact_pagos_compensados` section above) confirmed as the one that actually matches SAP's own period bucketing. A sample of 22 payments found 20 with `fecha_documento` in a different calendar month than `fecha_contabilizacion`. This affects how the existing Power BI dashboard's "Fecha Pago" groups payments by month. Deliberately not fixed as part of this change — would alter historical monthly totals already in production, needs its own validation pass first.

### `gold.vw_cartera_abierta` — line-by-line drill-down of open invoices, scoped to real customers
Built 2026-08-27, from the pending "Proposals in design" list. Source: `silver.sap_bsid`. **A view, not a table** for the same reason as `vw_cliente_canal_estatus`/`vw_pago_factura_simple` (criterion 4): `bsid` is a complete daily mirror with no history to preserve at line grain, and accumulating a daily snapshot at that grain was already rejected during `fact_saldo_cartera`'s own design (~91,593 line items would have grown ~33M rows/year against a known 2GB log ceiling) — this view only ever shows "as of right now," recomputed on every query.

**Original design (same day) reconciled exactly against `gold.fact_saldo_cartera`** by replicating its business logic with zero scope filter — validated with real data (total AND every aging bucket matched exactly). **Scope filters added later the same day**, after confirming with the business that `tipo_cliente <> SIN_RFC` (named `DIRECCION_ALTERNA` at the time, renamed later the same day), `canal_distribucion IN (10,40,60)`, and `estatus_comercial <> FUERA_DE_ALCANCE` should all apply here too — same 3 filters as `vw_pago_factura_simple` (channel `20` was tried and reverted the same day - see that view's own section above for why). **This deliberately breaks the reconciliation contract with `fact_saldo_cartera`**, on purpose: `fact_saldo_cartera` was deliberately left broad-scope (see its own section above), so `SUM(monto_firmado)` here is now "real, in-scope cartera," a smaller and more correct number for actual analysis than `fact_saldo_cartera.saldo_total`, not the same number anymore. If a daily TREND of this narrower number is ever needed (not just "as of today"), that requires a new dedicated snapshot fact — a view can't accumulate history `bsid` doesn't retain.

`dim_cliente_comercial` is an `INNER JOIN` here (was `LEFT JOIN` before the scope filters) — a customer with no comercial record can never satisfy the channel/status filters anyway, so `INNER JOIN` says that honestly. `dim_cliente_credito` stays `LEFT JOIN` (credit profile is enrichment, not a scope condition). Both are still joined temporally at **today** (not at any document date, since `bsid` has no "as of" concept of its own) — same as `fact_saldo_cartera`'s own Step 3.

## Retired objects (and why they're still documented here)

- **`gold.fact_aplicacion_pagos`** (removed 2026-08-19) — the 3-tier matching design (`REBZG`/unambiguous-group/no-match) had real over-attribution bugs: a $137 document could "explain" $2.5M in invoices within a massive compensation group, confirmed in several real cases. Replaced by the deliberately simpler design of `fact_pagos_compensados`/`fact_facturas_compensadas` + `vw_pago_factura_simple` — it only relates groups with exactly 1 candidate, with no match tiers or partial application. Less coverage, but without the risk of incorrect attribution.
- **`gold.fact_movimientos_compensados`** (removed 2026-08-13) — a complete line-level mirror of ALL of `bsad`. Explicit decision not to carry a whole silver table into gold undifferentiated — instead, build facts focused on specific business questions (the origin of `fact_aplicacion_pagos`, and later of `fact_pagos_compensados`/`fact_facturas_compensadas`).
- **`gold.vw_pago_virgen` / `gold.vw_factura` / `gold.vw_clasificacion_vencimiento_pago`** — prototypes from the design stage of `fact_aplicacion_pagos` and `clasificacion_cobranza`. The code already said "retired," but the actual `DROP` on the server was never run — found and cleaned up in the 2026-08-21 orphaned-object audit.
- **`gold.load_fact_pagos` / `gold.load_fact_facturas`** — procedures with the pre-rename name, internal body still pointing at tables that no longer exist. Orphaned for the same reason: the rename created the new objects but never `DROP`ped the old ones.
- **`gold.vw_comportamiento_pago_cliente`** (drafted and retired same day, 2026-08-27) — never deployed to the server. Meant to replace `fact_saldo_cartera`'s removed DPP columns, but a live view can only ever show "DPP as of right now," not a real trend over time - the user wants to analyze payment behavior across time, which needs either DAX time-intelligence (the chosen path, see `gold.vw_pago_factura_simple`'s section above) or a genuine periodic-snapshot fact, never a view.

## Proposals in design — not yet implemented

Documented here because the full design was already discussed, but building them is still pending work:

- **Credit utilization** — **not as a SQL view, as a DAX measure** (`DIVIDE(SUM(saldo_total), SUM(limite_credito))`) directly in Power BI, since `fact_saldo_cartera` and `dim_cliente_credito` are already related in the model. A precomputed view or column would invite someone to average it incorrectly (averaging already-computed ratios is mathematically incorrect at any grain other than the row's exact grain).
- **Stage 2 of the collections report** ("expected budget" — overdue/upcoming balance at the start of the month) — `vw_cartera_abierta` only solves the *forward-looking* half (from today onward). Retroactively reconstructing past months requires combining `bsid` (what's still open today and was already open on that date) with `bsad` (what was open on that date but has since been settled) — a non-trivial design, still unresolved.
- **Collections management, write-offs/bad debt, credit-limit approval** — real business processes with no confirmed data source yet. Not designed until confirming with the team where that information lives (SAP, Excel, another system).
